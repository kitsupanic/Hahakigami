# Keep one scan per disk instead of one Current scan

The app held a single live scan, the **Current scan**. Scanning a second disk threw away the first disk's results the moment the new scan started, even though the sidebar's Disks list invites people to treat each disk on its own. Each disk now has its own scan slot. A disk keeps its latest scan in memory, rescanning it replaces only that scan, and ejecting the disk frees it. Every folder scan shares one more slot, as the Current scan did for folders. Running disks in parallel was a separate change: `0004-scan-disks-in-parallel-on-one-budget.md`.

The backend replaces `AppState.session` with `LiveSlots`, a map keyed by a `Slot`: `Slot::Disk(root path)` for a volume target (`Target.volume`) and `Slot::Folder` for every other target. The saved-scan slot is unchanged. The frontend mirrors it with one summary per slot. The sidebar loses its Current scan row: each disk row shows Scanning or Scanned and opens its own results, and a folder scan gets one extra row after the disks.

## Consequences

- Starting a scan replaces and invalidates only its own slot's previous scan, and only that scan is used as the incremental-rescan baseline. Other disks' scans are never touched, emptied or invalidated. A start was refused while any scan ran. That gate narrowed to the slot's own scan when parallel scans landed (ADR 0004).
- A cleanup invalidates only the scan it cleaned (it already worked on one session), so other disks stay valid.
- Ejecting a disk calls the new `discard_scan` command: the scan is cancelled if it is running and its slot is freed at once. The frontend drops the slot, and if its results were on screen the welcome page opens with the startup disk selected. A late event from the discarded scan finds no slot and is ignored. A folder scan is not tied to a disk and is never dropped by an eject.
- A discarded scan that is still running moves to a `draining` list instead of vanishing. It cannot be found, but it still counts as running for the gates that need no scan at all, so calibration and the saved-scan operations wait for a walk that may be stuck on the ejected mount. The frontend holds the same wait until the scan's channel reports an end. Other scans may start meanwhile (ADR 0004).
- A queue "Scan" registers its target with the same disk rule as the Disks list, so rescanning an entry under "/" or `/Volumes/X` uses that disk's slot and baseline.
- Memory grows with the number of scanned disks (about 130-140 bytes per file) and is released only by a rescan of the same disk or an eject. There is no cap.
- Each cleanup queue entry is matched to one live scan: the scan of its own root if there is a usable one, otherwise the usable disk scan with the longest root containing the item (never a folder scan). So an item queued from a folder still counts when its whole disk has been scanned, entries from several disks show their own statuses, and a cleanup or eject on one disk changes only the entries matched to that disk's scan. The match is re-derived on every read from root and item paths, and the item is always verified through the matched scan itself. A review or commit is addressed to one scan (one disk at a time). The CLI and MCP `current` is unaffected by disk slots: they run in their own process with their own `automation::Service`, which never touches `AppState` or `LiveSlots`, so `current` there is that process's own latest scan.
- Scan events are routed by scan id: a scan keeps updating its row while another disk's results are on screen, and Rescan of a scanning slot stays off until its scan stops.
- The scan progress bar moves from the removed Current scan row onto the scanning disk's row (a folder's bar is indeterminate). The compare dialog (off while saved scans are off) still calls the live scan on screen "Current scan".
- Switching between disks resets the explorer's focus, selection and history; per-disk navigation state is not kept.
