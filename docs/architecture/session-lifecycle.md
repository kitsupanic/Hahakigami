# Scan session lifecycle

## Saved scans disabled
Saved scans are switched off by `SAVED_SCANS_ENABLED` in `src-tauri/src/lib.rs` (currently `false`). While off:
- These desktop commands return "Saved scans are turned off in this version.": `save_scan`, `list_saved_scans`, `begin_saved_open`, `open_saved_scan`, `rescan_saved_scan`, `delete_saved_scan`, `import_saved_scan`, `export_saved_scan`, `compare_saved_scans`, `compare_current_scan`.
- The frontend asks `saved_scans_enabled` first, then skips `list_saved_scans` and does not reopen `lastOpenedId`. Save, Import, Export and Compare are disabled in the menu and UI, and the sidebar's Saved scans section and its Compare scans and Import scan buttons are hidden.
- CLI/MCP `scan` still runs but does not store the result. CLI `list`, `summary`, `node`, `children`, `search`, `issues` and the MCP equivalents refuse any saved ID; MCP `status`, `cancel` and queries on `"current"` still work.
- Library files on disk are not touched or deleted.

To re-enable: set `SAVED_SCANS_ENABLED` to `true` and remove the `#[ignore = "saved scans disabled: SAVED_SCANS_ENABLED"]` markers (`rg SAVED_SCANS_ENABLED`). The sections below describe the behaviour when it is on.

How the backend (`src-tauri/src/lib.rs`) and frontend (`src/createApp.svelte.ts`, with the scan slots in `src/scanSlots.svelte.ts`) hold scan results. Terms follow `GLOSSARY.md`: **Disk scan**, **Saved scan**, **Scan target**. Cite functions, not line numbers. The decision to keep a scan per disk is in `docs/adr/0003-per-disk-scan-slots.md`; running them in parallel on one shared budget is in `docs/adr/0004-scan-disks-in-parallel-on-one-budget.md`.

## Backend slots (`AppState`)
`AppState::scans` (`slots::Slots`) holds all of this; see "The slots module" below.
- The live slots hold the **Disk scans**: at most one live session per `Slot`. `Slot::Disk(root)` is the slot of a volume target (`Target.volume`, looked up in `state.targets` at start), keyed by its registered root path. `Slot::Folder` is shared by every non-volume target. Filled only by `start_scan_impl` (via `start_scan` and `rescan_saved_scan`). Origin `Live`.
- `draining` holds discarded scans that were still running. They are not findable by `find`, and they do not stop a scan starting in any slot. The no-scan-at-all check counts them, and it releases each one once it has ended. They keep their share of the scan budget until their thread ends.
- Whether the scan in one slot runs is the only thing that stops a start (`Slots::replace`): scans in different slots run at the same time. The no-scan-at-all check (`require_idle`: any slot, or a draining scan) is for what cannot overlap a scan at all: see "Parallel scans".
- The cleanup queue matches entries against every slot (`Slots::sessions` lists them for `cleanup::statuses`, which offers the usable ones to `cleanup_queue::statuses`). `Slots` keeps no "latest" slot: the CLI and MCP `current` is the automation service's own latest scan, in its separate process (`cli.rs`, `automation.rs`), and is unaffected by disk slots.
- The saved slot is the **Saved scan** slot. Filled only by `open_saved_scan` (decoded from the library). Origin `Saved`. At most one saved scan is open.
- The live slots and the saved slot are independent. Opening a saved scan does not touch any Disk scan, and a new scan does not touch the open saved scan.
- Each slot holds an `Arc<Session>` with its own `id` (a fresh UUID), snapshot `store`, `valid` flag and caches.
- The automation service (`automation.rs`: CLI and MCP) has its own single-scan model and never touches these slots.

### The slots module (`slots.rs`)
Commands reach scans only through `slots.rs`. It owns the live slots (with `draining`), the saved slot and the scan budget (`budget.rs`). `Session` and `Slot` are defined there too. `ActivityGate`, the target maps and the automation service stay outside it.
- `find(id)`: the scan with that id in a live slot, else the saved slot, refused if it is no longer valid. It takes no lock, so the read-only explorer queries use it.
- `Session::hold(need)` on a found session: takes its `operation` lock and checks it is a live scan (not a saved one) that is still valid. `Need::LiveCompleted` also refuses a scan that is still finishing. `held.completed_snapshot()` then reads the store and checks `Completed`. Every command that changes state or acts on files holds the scan this way, at the point where it used to take `operation` by hand. `Need::Live` is for what works on a scan that is still walking (`reveal_node`, and Quick Look's file check): it does not ask for a finished scan.
- `Session::peek_completed()` is `hold(Need::LiveCompleted)` plus `completed_snapshot()` without the `operation` lock, for callbacks that must not wait on a cleanup (Quick Look's authority check, `preview_item`, and the cleanup queue's usable-scan test). `Session::check_valid()` is for a read-only query that re-checks the flag after it read the store.
- Lock order: `operation`, then the cleanup queue, then the snapshot store. `Held` reads the store only on `completed_snapshot()`, never up front, so it cannot reverse `cleanup::queue_view`'s queue-then-store order.
- `replace(key, request)`: refuses if that slot's own scan runs, then takes the budget grant, invalidates the old session, takes the rescan baseline and installs a `Session::live`, in that order. Nothing changes if it refuses. It returns the session, the baseline and the `Grant` for the scan thread.
- `discard(id)`: cancels, invalidates and drains (ADR 0003).
- `open_saved(session)` and `close_saved(saved_id)`: swap in an opened saved scan (invalidating the one it replaces) and close the open one when its library entry is deleted. `is_live(session)` says whether a session still sits in a live slot.
- `sessions()`: every live scan, disk slots first, for Cleanup queue matching.
- The no-scan-at-all check (`require_idle(reason)`) takes the caller's reason ("…before opening saved results.", "…before restarting.") and counts draining scans. `idle_exclusive(gate, reason)` is `Activity::begin` followed by that check.
- One message per reason, whichever command meets it: "Results changed after cleanup. Rescan this location." (the scan was invalidated), "Wait for a completed scan first." (running, finishing, cancelled or failed), "Saved scans are historical results. Scan this location again before file actions." and "This scan is no longer active."
- A session's `valid` flag is private. It goes false only through `Session::invalidate()`: on replace, discard, opening another saved scan, and a cleanup that trashed something.

### The cleanup module (`cleanup.rs`)
The Trash path. Commands only take the `Activity`, close Quick Look (commit), take the `access_setup` lock (commit) and move the work off the async workers.
- `review(s, Pick::Nodes(ids) | Pick::Queue(queue, sessions))`: holds the scan (`Need::LiveCompleted`), builds the items (`selection`) and their views, and replaces the scan's ticket. A queue review keeps the queue locked until the ticket records its revision.
- `commit(s, queue, token, queued, trash)`: holds the scan, spends the ticket (token, expiry, queue revision), verifies every item on disk, then verifies and moves each one with `trash`, records the outcomes in the queue and invalidates the scan if anything moved. `trash` is the seam: `native_trash` (`platform::trash`) in the app, a recording fake in tests.
- `add` (queue a selection) and `queue_view` (the queue as the UI shows it).
- Targets: `retain_target` in `lib.rs` is the one place that records a target with its guard. `register` reads a fresh guard first; `cleanup_queue_target` passes the entry's recorded one.

### What replaces or invalidates a slot
- New scan (`start_scan_impl`, through `Slots::replace`): refuses only while that slot's own scan is running ("This disk is already being scanned. Cancel that scan or wait for it to finish first.", or the folder wording), or when the scan budget has nothing left. Otherwise it replaces only the target's own slot: that slot's old session gets `valid` false and an empty running session takes its place right away. The old scan is gone from that moment, before the new one has any data. Other slots are never touched or invalidated, running or not. Every refusal happens before any slot changes.
- Opening another saved scan: `open_saved_scan` invalidates the old saved session and swaps in the new one (`Slots::open_saved`). It does this only after the archive decodes and `mark_opened` succeeds. Any load, cancel or persistence failure leaves the old saved session in place. It is refused while any live scan is running; finished ones are fine.
- Import (`import_saved_scan`) and export only touch the library. They never fill or clear a slot. They are refused while a live scan runs.
- Cancel or fail: the session stays in its slot with state `cancelled` or `failed`, with partial results, until the next scan of that slot replaces it. Save and compare require `Completed`.
- Cleanup: `cleanup::commit` sets `valid` to false on the session it cleaned, if anything was trashed. Other slots stay valid. The slot is not cleared; the user must rescan that disk. Saved sessions are never cleaned up (`hold` refuses them).
- Eject: `discard_scan(scan_id)` removes the session from its slot and sets its `cancel` and `valid` false. If it is still running it moves to `draining`, so the gates that need no scan at all (setup, restart, saved-scan open/import/export/compare) stay closed until the walk really ends, even if it hangs on the ejected mount. Other scans are not held up. Memory is freed once the scan thread ends. An unknown or already discarded ID is a no-op. Only live slots are discarded.
- Deleting a saved scan from the library (`delete_saved_scan`) closes the open saved scan if it is that entry (`Slots::close_saved`), so it cannot stay open; a live scan is untouched.

### Stale session IDs
- `Slots::find(id)` searches every live slot, then the saved slot, for a matching `id`. No match returns "This scan is no longer active." A match that is no longer valid returns "Results changed after cleanup. Rescan this location."
- Anything that mutates or acts on files holds the scan (`Session::hold`), which rejects Saved sessions: `save_scan`, `quick_look_node`, `reveal_node`, `compare_current_scan`, `prepare_trash`, `prepare_cleanup_queue`, `commit_cleanup` and `add_cleanup_queue`.
- `compare_current_scan` holds its scan like the others, so a saved scan's ID is rejected there as historical.
- `cleanup_queue_target` registers a fresh target for the entry's recorded root. It sets `volume` with `platform::is_disk_path`, the same rule `discover()` uses, so a queue rescan of "/" or `/Volumes/X` uses the disk's own slot. Any other root is a folder target.
- `rescan_saved_scan` does the opposite: it needs a Saved session. It reads the root path from it and re-registers that path as a fresh Scan target (historical identities grant no filesystem authority; the new target is not a volume, so it uses the folder slot). It then runs the normal scan start.
- The cleanup queue view (`cleanup_queue::view`, built from `cleanup_queue::statuses`) matches each entry to one live scan. Entries are keyed by root path and item path, with no scan id, so this is decided on every read:
  1. **Own root.** The scan whose snapshot root equals the entry's recorded root (a disk scan wins over a folder scan of the same root). Its checks are the strictest: the root's identity and ancestors must equal the record, the item must be found in the scan (else `missing`), and its identity and ancestor chain must equal the record.
  2. **Covering disk.** If no usable scan has that root, the usable Disk-slot scan with the longest root that contains the item's path (component-wise prefix). Folder scans never cover another root. The item must be found in that scan, not be an excluded node, and have the recorded identity and ancestor chain; otherwise the disk scan is stale or does not cover it and the entry has no status (an own-root scan reports `changed` instead). A match that then fails the on-disk check is `blocked`. The queued root's identity is not compared with the disk scan's root. It is part of the item's recorded ancestor chain, and that whole chain (queued folder up to `/`) must equal the chain the disk scan holds for the item.

  The rules live in `cleanup_queue.rs` and take only data: the queue, `safety::Scan`s (id, disk or folder, snapshot, root ancestors, volumes), the home folder and the mounted paths. `statuses` in `cleanup.rs` is the one adapter that turns live sessions into scans, so they can be tested without a Tauri app or a `Session`. A disk scan wins over a folder scan of the same root whatever the order of the scans. Items are looked up by walking child names down from the scan root (`safety::node_at`), one lookup per entry, not by building every node's path (a snapshot with recorded path spellings falls back to one traversal). A scan is usable if it is live, valid, not running and Completed (checked by `cleanup::statuses` before it offers the scan). An entry with no match, or one whose covering scan does not hold the item, has no status: it reads "needs scan". That covers a running, cancelled or failed scan, one invalidated by a cleanup, a discarded (ejected) one, and a root or disk with no scan. Other statuses are `ready`, `missing` (own-root scan only), `changed` and `blocked`. The view also reports `matchedScanId`, the scan an entry was matched to, and a cleanup or eject on one disk changes only the entries matched to that disk's scan.
  - **Volume.** (device, inode) is not enough on its own: a removable volume reformatted and mounted at the same `/Volumes/<name>` can reuse the device number, and FAT/exFAT file IDs come from on-disk layout. When a live scan completes, `scan_volumes` reads the volume UUID (`getattrlist` `ATTR_VOL_UUID`) of each volume region into `Session::volumes`, keyed by the region's root node. A region starts at the scan root, at a device change (a mount) and at each startup-disk firmlink (`disk_scan::firmlink_paths`, from `/usr/share/firmlinks`): the System and Data volumes share one `st_dev`, so a device number alone would give Data items under `/` the System volume. Excluded nodes are skipped; a region whose volume cannot be read is left out, and its items fail closed. A `CheckedItem` and a queue entry carry the volume of the item's nearest region (`safety::checked_item`) (`safety::Volume`: a UUID, or `NoUuid` for a filesystem without one). Under both rules an entry whose recorded volume differs from the matched scan's, or that has none (queued by an older version), is not ready (own root: `changed`; covering disk: no status). This comparison is in memory: `cleanup::statuses` is polled by the UI and never reads a volume. `safety::verify` reads the item's volume again just before Trash and refuses an unknown or different one (`verify_paths` is the same check without that read).
  - A scan of `/` never holds items under `/Volumes` (`traversal_allowed` in disk-scan skips them), and a volume's scan stays on its device, so an item on another mount is not found there and reads "needs scan". `/` records startup-volume paths in their public form (`/Users/...`; the firmlink copies under `/System/Volumes/Data` are excluded), the same form a folder scan records. A path spelled differently is simply not found.
- `prepare_cleanup_queue` and `commit_cleanup_queue` are addressed by scan id. The review matches the queue against every live scan, like the view, and takes the ready entries whose `matchedScanId` is that scan (`cleanup_queue::ready_nodes`) (its own root's entries, plus entries of folders inside it when it is a disk scan). The items of the ticket are rebuilt from that scan's own nodes (`cleanup::selection`: `safety::checked_item` for identity and ancestors, then `safety::verify` against the scan's root), then verified again on disk just before Trash. Commit invalidates only that scan. Entries matched to other scans stay queued, so a queue holding entries from several disks is cleaned one disk at a time: open that disk's scan, review, commit.

## Parallel scans
Scans in different slots run at the same time. `docs/adr/0004-scan-disks-in-parallel-on-one-budget.md` has the reasons.
- **Scan budget** (`budget.rs`, owned by `Slots`): one pool of workers (`min(CPU threads, 16)`, the same cap as one scan's settings) and retained descriptors (`disk_scan::default_descriptor_limit()`: `RLIMIT_NOFILE` less 64, clamped 1..512). `Slots::replace` takes a `Grant` after every other check and before it replaces anything. Alone, a scan gets what it asks for (workers: the larger of its worker count and its cached-validation count; descriptors: half the total). Beside other scans it gets at most half of what is still free, rounded up. Workers never refuse a start: a scan always gets at least one, so the process can run a thread or two over its total. Descriptors are a hard total with a floor of 8 per scan; the start is refused only when none are left ("Other scans are holding every file this app may keep open ...", after seven scans with 512). Scans already running keep their share; nothing is rebalanced. `raise_descriptor_limit()` runs at the start of `run()` and lifts the process's own soft `RLIMIT_NOFILE` toward the hard limit (cap 10240), so a Finder launch's 256 does not shrink the shares.
- The session's `workers`, `cached_validation_workers` and `descriptor_limit` are capped to the grant. `ScanOptions::descriptor_limit` carries the descriptor share into every scanner call of the scan, including the speculative rescan (`prepare_rescan`) and clone validation.
- The `Grant` moves into the scan thread and is dropped just before the scan reads as ended (`finishing` false), so it is returned on completion, cancel, failure, and a panicking thread. A discarded (draining) scan returns it when its thread ends.
- A panic in the scan thread is caught (`catch_unwind` in `start_scan_impl`; `end_panicked_scan`): a running session becomes Failed with "The scan stopped unexpectedly.", a finished one keeps its results with a cache warning, `finishing` is cleared and a final event is sent. Without this the slot would read as running forever and the gates that need no scan would stay closed.
- **Activity gate** (`ActivityGate`): scan starts hold it shared, so several can begin at once. Every other holder (library, cleanup, queue edits, Quick Look, reveal, restart) is exclusive: it refuses another holder and any start in flight, and a start refuses while one is held. Cleanup of a disk therefore waits only for starts in flight, never for another disk's running scan, and it invalidates only its own session.
- **Gates that still need no scan at all** (`Slots::require_idle`, draining scans included): first-run setup and restart (`setup_idle`), saved-scan open (`open_saved_scan`), import and export (`portable_activity`), and comparison (`compare_saved_scans`, `compare_current_scan`). Each is checked while its exclusive `Activity` is held, so no scan can start between the check and the work.
- **Rescan cache**: every probe, record check, refresh and save goes through the one cache lock, which `baseline.rs` owns (`Baselines`, poison tolerant, so a scan that panicked holding it does not break the others) and holds it for the whole call. Nothing outside that module locks it. Scans that finish together publish one after the other, never interleaved: `save` prunes to 8 entries and 512 MB inside the same lock, and entries of the same root replace each other. Decoding a cached baseline is the exception: `Cache::begin_load` confirms the record under the lock and `Pending::decode` reads the archive without it, so one disk's decode does not delay another disk's publication. A published archive never changes; if pruning removed it in between, the decode fails and the scan falls back to a full one. A scan starting while another one publishes still waits for the lock (`save` holds it for the whole write, which keeps another scan's sweep from deleting an archive that is written but not yet recorded), so its first progress event can be late.
- Progress: each start has its own `Channel<Summary>`; events update the slot with their scan id, and the displayed summary only when that scan is on screen. The scan run (`run_scan`, `end_panicked_scan`, through `start_scan_impl`) reports to a `Progress` port: the channel in the app, a `Recorder` in tests, which waits for the final report (phase `done`, sent once the scan no longer reads as running). A failed report cancels the scan.

## Frontend: which result is shown
- `session.summary` is the displayed `ScanSummary`. `historical` is `summary.origin === "saved"`. Commands are addressed with the displayed `summary.scanId`, except comparison, which uses the scan ID of the live scan on screen (`comparableCurrent`).
- `scans` (`createScanSlots` in `src/scanSlots.svelte.ts`; `createApp` builds one, and `app.scanSlots` is its `slots`) mirrors the backend: one entry per disk path plus `FOLDER_SLOT`, each `{ target, scanId, summary }`. `slotKey` is the one place-to-slot rule, the backend's (`start_scan_impl`): a volume target is its disk's slot, anything else is the folder slot. `summary` is null only between a scan's start and its first event. `slotScanning` is true for such a slot or a `running` summary. `app.shown` (in `createApp`) is the one answer to "which scan is on screen": `{ summary, slot, target }`, null on Home or with no scan; `slot` and `target` are null for a saved scan. App.svelte, the sidebar and `can.*` read it or `app.summary`, never a view-local copy. The module asks the backend only through a port (`start_scan`, `rescan_saved_scan`, `cancel_scan`, `discard_scan`, `scan_summary` and the event channel): `tauriScanPort` in the app, a fake in `src/scanSlots.test.ts`. It never touches the view: for each start it calls the app's `beginStart` (in `createApp`), which runs the app-level gates and returns the `StartView` the module then reports to.
- Progress events route by scan id. The module's `record` updates the slot whose `scanId` matches, then tells the start's view, which replaces the displayed `summary` only when `activeId` is that scan. A scan that was replaced, cleaned up or discarded has no slot, so its late events change no slot. Once the scan's ID is known, its events no longer depend on the view generation, so opening other results does not stop a running scan's updates.
- The frontend Cleanup queue is `createCleanupQueue` in `src/cleanupQueue.svelte.ts` (`app.cleanupQueue`). It owns the queue view, its busy flag and error, the load epoch (a reply a newer load or change overtook is dropped) and the refresh deferred while a change runs, plus what is derived from the queue: `readyHere` (ready entries matched to `app.shown`), the per-root `groups`, the `tally` and the explorer `selection` against the queue. It reaches the backend only through `QueuePort` (`tauriQueuePort`; `fakeQueuePort` in `src/testCleanupQueue.svelte.ts` for `src/cleanupQueue.test.ts`) and asks the app through hooks for its gates (`mutable`), the cleanup report to update and the selection. Gates on the scan on screen (`sessionBlocked`, a completed live summary) stay in createApp's wrappers (`addQueue`, `scanQueue`, `prepareQueue`).
- `liveTarget` (reactive) is the Scan target of the live scan on screen, or the one last on screen while a saved scan is shown.
- `parkedSaved` is the open saved scan's summary while a live scan is displayed. The backend still holds its results. There is no parked live scan: the slots hold them.
- Switching: `showSlot` opens a slot's scan through `resetView` and `showResults`. A slot whose scan has not reported yet (`summary` null) opens as an empty view with `activeId` set to its scan id: the welcome page for that disk, filled by its first event. `openDisk` (disk rows and the folder row) selects the target and calls `showSlot` if the slot exists, otherwise `showHome`. It does nothing while `sessionBlocked`. The `openSaved` fast path (`parkedSaved?.savedId === id`) swaps summaries the same way. None of these run a scan or open command. Only the first open of a saved scan calls `begin_saved_open` and `open_saved_scan`. Navigation state (focus, selection) is reset on every switch.
- `start` (new scan or `rescan_saved_scan`; `createApp.start` calls `scans.start`): each start has its own channel and its own `StartView`. A channel carries one scan's events, so the first event, or the returned id, registers the target's slot as a placeholder for the new scan whatever the user has opened since. The view's `accepted` then runs, and only if no newer start or navigation happened (`g === generation.current` in `beginStart`) does the start also take the view: it moves a displayed saved scan to `parkedSaved` and resets the explorer. Other slots keep their scans, so starts can overlap and none is lost. `busy` is `opBusy` (trash review, cleanup) or `scans.starting`, the starts in flight, instead of being set and cleared by whichever finished last. The app gates a start in `beginStart` (the folder picker, the library, a pending Quick Look, Full Disk Access). The module checks only its own slot, and hands the backend's refusal to the view's `failed`, which shows it or opens the Full Disk Access dialog. A rescan after a cleanup first drops the cleaned scan's slot (`scans.drop`).
- Starting a scan needs only its own slot free. `scans.busy(place)` is true while the slot of that place scans (a slot without a summary yet counts as running); `scans.folderBusy()` is the folder slot, which the rescan of a saved scan uses because `rescan_saved_scan` registers a folder target. `can.rescan` and `can.rescanDisplayed` use them for the place the click would scan, so the welcome page's Scan button is enabled when the selected target's slot is not scanning, and the toolbar Rescan acts on the displayed slot. Other disks scanning, Choose folder and the disk rows do not block it. `scans.start` refuses a busy slot itself. Stop acts on the displayed scan.
- **Scan all disks** (`scanAllDisks` in `createApp`, gated by `can.scanAllDisks`, runs `scans.scanAll`; Disks header button, welcome-page button and File menu item) scans `localDisks`: Disks-list targets with `volume` and `local === true`. `local` comes from the mount table's `MNT_LOCAL` flag (`platform::mounted_flags`, `is_local_mount`), read in the same `getfsstat(MNT_NOWAIT)` call as the mount list; a path is non-local only when a mount at exactly that path lacks the flag, and `discover()` never calls `statfs` per path for it. `can.scanAllDisks` is `can.rescan` without the per-slot check, plus: there is at least one local disk, and no Scan all is being started (`scans.scanningAll`, which also spans the wait for cancelled scans). A start in flight already closes it through `busy` (`sessionBlocked`). A disk whose slot is scanning is cancelled (`cancel_scan`, errors ignored because a scan in its caching phase refuses and ends on its own) and `scans.scanAll` waits for that scan's final non-running event (`restarting`, 30 s cap, then that disk reports "The scan did not stop in time."), then starts it, unless the disk was ejected meanwhile. Idle disks start at once, in parallel.
- **Scan all and the view**: `scanAllDisks` gives `scans.scanAll` a `takeView(key)` predicate, and the module passes its answer to `beginStart` for each disk's start. Only the start of the disk whose results were on screen when Scan all was pressed (else the selected disk) takes the view, and only if the selection, the welcome page state and the view generation are still as they were at the press. The other starts use no generation (`g` is -1), so they never take the view: they only fill their slots and sidebar rows. A selected folder (or any other selection) keeps its results on screen.
- **Scan all failures**: A Scan all start's refusal reaches `scans.scanAll` even when a newer start overtook it (the view's `failed` returns false for it). The failures come back as one line per disk, `scanAllDisks` shows them in one error message, and they never stop the other disks. `FULL_DISK_ACCESS_OFF` is the exception: `failed` handles it, setting access off and opens the Full Disk Access dialog once for the whole Scan all, with the blocked request marked `scanAll`, so "Scan anyway" runs `scanAllDisks` again for every disk. A Full Disk Access check before the first start does the same. A restarted scan's cancel does not raise the "Scan cancelled" toast.
- **Batch indicator** (in the module): `batchKeys` holds the slot keys of scans started since every scan last ended and no start was in flight (any trigger; a restart keeps its entry, so it counts once; a slot whose scan Scan all cancelled and has not started again, `awaitingRestart`, still counts as running). `batchProgress` is `{ done, total }` only while 2 or more slots run (`done` = batch slots whose scan finished, was cancelled or failed), else null. The Disks header shows it as "Scanning · N of M done" in an `aria-live="polite"` region whose text changes only when N or M does.
- `idle` (and the saved-scan handlers, Settings and the saved-scan sidebar controls) still require `!scans.anyRunning` (`app.anyScanRunning`): no slot scanning, and no ejected disk's scan still `draining` (its scan id is held until the channel reports a non-running state). They match the backend gates that need no scan at all.
- The cleanup queue is re-read (`refreshQueue`) whenever the displayed scan or any slot's scan changes id or state (`scans.signature`): a scan of any disk completing, failing, being cancelled, replaced or dropped. Progress that changes neither does not refresh it. Each disk's section on the queue page offers "Review N ready" when the scan on screen has ready entries for it (`readyHereEntries`: `matchedScanId === summary.scanId`, so the frontend never re-derives the match), and "Scan <disk>" while any of its entries can't be reviewed from that scan. The review is addressed to the displayed scan, so it covers all of that scan's ready entries, including ones in other sections. Each section's band splits its bytes into reviewable, ready-but-not-in-this-scan (`status: ready`, other `matchedScanId`) and not-ready entries (`queueBands.ts`).
- `scanQueue` (queue "Scan") starts the entry's target. If it is a volume already in the Disks list, that existing target is selected and no second row is added.
- Eject: when `refreshDisks` finds a volume gone, `dropEjected` calls `scans.discard` for each of its disks: the backend frees the scan (`discard_scan`), the slot is dropped, and a scan still running is held as `draining` until its channel reports an end. If that scan's results were on screen, the summary is cleared and the welcome page opens with the startup disk selected (the volume for "/", else the first volume, else the first target); results hidden behind Home or the queue do not move the selection. The cleanup queue is refreshed. A folder scan is never dropped by an eject.
- On launch, the startup code that calls `list_saved_scans` opens the library's `lastOpenedId` through `openSaved`.

## Save
- `save_scan` reads the live scan's snapshot (it holds the scan with `Need::LiveCompleted`: `Live`, valid, `Completed`, not `finishing`) plus its metadata (times, workers, QoS). It takes `Activity` and the scan's `operation` lock for the duration.
- The scan stays in its slot. Nothing is replaced and no saved session is opened.
- The frontend (`saveScan`) only links it by setting `savedId` on the displayed summary and its slot's summary, so Save is not offered twice. The backend `Session.saved_id` stays `None` for live sessions.

## Comparison
- `compare_saved_scans(before_id, after_id)`: both sides are decoded from the library one after another. The first is reduced to a `comparison::Baseline` before the second loads, so only one decoded archive is in memory at a time.
- `compare_current_scan(scan_id, saved_id, current_after)`: the live side comes from the in-memory `store` of the live slot with that id. The saved side is decoded from the library. `current_after` sets which side is "after". It needs a completed, valid, non-running live scan.
- Same-root rule: `Baseline::compare` rejects scans whose snapshot root paths differ byte-for-byte. The UI (`CompareScans.svelte`) only offers saved scans with the same `rootPath` as the other side. The live scan's path comes from `liveTarget`. The dialog still labels it "Current scan".
- Nothing is written to disk. Comparison does not replace a session, create file authority or change the startup selection.
- The frontend (`compareScans`) picks `compare_current_scan` when either ID equals `comparableCurrent.id`, otherwise `compare_saved_scans`.

## Incremental rescan baseline
- In `Slots::replace`, the old session of the slot being started has its snapshot moved out (`mem::replace` with an empty snapshot) as `previous: baseline::Taken`. That happens only if that session is `Live`, has a `cache_token` (cache was published), has the same root as the new scan, and passes `baseline::eligible`. Other slots' sessions are never used or emptied.
- `run_scan` hands it to the baseline module, which uses it as the in-memory baseline if the epoch matches and `cache::recent` holds. Otherwise the module probes the disk cache. The old session has already been invalidated, so its emptied snapshot is never served.

### The baseline module (`baseline.rs`)
The **Rescan baseline** (`GLOSSARY.md`): whether a scan starts from an earlier one, and keeping its result for the next. `run_scan` reaches the rescan cache and the filesystem event journal only through it. `cache.rs` is the on-disk store behind it and `events.rs` the journal.
- `Baselines::acquire(journal, request, started)`, before the scan: takes the journal cursor before anything is replayed or walked, picks the in-memory baseline or probes the disk cache, replays the journal while the archive decodes (off the cache lock), runs the speculative rescan (`prepare_rescan`), resolves aliases and checks the epoch again. It returns a `Start`: `Prepared` (the speculative rescan already is the result, kept only when the journal reported nothing and the scan was not cancelled), `Seed` (scan incrementally from it) or `Full` with the reason shown as the fallback. `started` runs once the cursor is taken and before the baseline is chosen: `run_scan` sends the scan's first report there.
- It also returns a `Ticket` when the root has event history. `Ticket::publish(snapshot, cancel, scan, about_to_write)`, after the scan: publishes only a clean, uncancelled result, refreshing the existing record when nothing changed and saving otherwise, inside one lock take. `about_to_write` runs only when it will publish (`run_scan` reports the `caching` phase there). It returns the token for the session's `cache_token`, with a warning if the write failed: the token is kept either way, because the in-memory baseline does not need the disk record. Dropping the ticket publishes nothing.
- It takes plain values, not the `Session`: `run_scan` applies mode, fallback reason, cache warning and token to the session.
- `Journal` is the seam for the event journal (`history`, `cursor`, `replay`): `Fsevents` in the app, a scripted fake in the module's tests, so the default tests drive the real order.
- `slots.rs` takes the old session's snapshot (`take_baseline`) and asks this module whether it can be one (`baseline::eligible`).

## Gotchas
- `App.svelte` has a local `summary = app.shown?.summary`. It is null while the welcome page is shown. Command handlers and menu actions must read `app.summary`, not the local value.
- Race: a command holding an `Arc<Session>` that gets replaced mid-flight sees `valid == false` and returns the "after cleanup" message, even if the cause was a replacement.
- A new scan discards the previous scan of its own slot immediately, not on completion. Cancelling the new scan does not bring the old one back. Other slots are unaffected.
- A discarded scan that never ends (a walk stuck on a dead mount) keeps setup and the saved-scan operations refused until the app restarts: the backend and the frontend both wait for it. It also keeps its share of the scan budget, so later scans get a little less.
- A queue entry reads "needs scan" while its scan runs, after a cleanup on that disk, and after that disk is ejected, unless another usable disk scan covers its item. Other disks' entries keep their status.
- `cancel_scan` and `scan_summary` use `session()`, so they accept a saved scan's ID too. Cancelling a saved ID is a no-op.
- A summary re-fetched from the backend for a live scan never has `savedId`. Only the frontend's local copies have it.
